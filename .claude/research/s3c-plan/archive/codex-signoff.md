# S3c plan review — Codex

## Verdict: conditional sign-off

## Required changes (if any)
- Task 3, Task 5, Task 11a: do not let `received` travel through the generic status-update path. The shipped UI still marks ordered POs as `received` via `updatePurchaseOrderStatus()` from the row action menu, which bypasses roll creation and `actual_delivery_date` updates (`app/dashboard/inventory/purchase-orders/_components/use-po-actions.ts:59-69`, `app/dashboard/inventory/purchase-orders/_components/po-table.tsx:254-258`, `src/infrastructure/services/purchaseOrderService.ts:342-389`, `src/infrastructure/services/purchaseOrderService.ts:425-519`). Make `received` reachable only through the receive flow/UI.
- Task 5: remove `PARTIAL_RECEIPT_REJECTED` unless product is explicitly changing behavior. Current TS receive logic allows partial receipts and returns `partialReceipt` instead of rejecting them (`src/infrastructure/services/purchaseOrderService.ts:494-519`, `src/application/services/purchase-order.service.interface.ts:18-24`).
- Task 6, Task 9, Task 11b: preserve the actual reorder suggestion contract, not just stock + urgency. The current UI depends on pending-PO suppression, `daysUntilStockout`, `pendingQuantity`, supplier resolution, and `normal -> medium` urgency normalization (`app/dashboard/inventory/reorder/_components/reorder-data-fetcher.ts:52-74`, `src/application/use-cases/reorder/generate-reorder-suggestions.use-case.ts:22-148`, `app/dashboard/inventory/reorder/_components/reorder-suggestions-table.tsx:190-276`). The draft underspecifies this.
- Task 7, Task 9, Task 10, Task 11b: include the shipped bulk reorder actions or explicitly defer them. The reorder page has three create paths today: row-level create, “Create Individual POs”, and supplier-grouped “Create Bulk PO” (`app/dashboard/inventory/reorder/_components/reorder-suggestions-table.tsx:148-168`, `app/dashboard/inventory/reorder/_components/reorder-po-handlers.ts:46-332`). The draft only covers the row button.
- Task 8, Task 9, Task 11c: point the cutover at the real CSV commit surfaces. `app/dashboard/inventory/import/page.tsx` parses client-side and commits reviewed rows through `rollService.bulkAddRolls()`, not `csvService.processCSVFile(file)` (`app/dashboard/inventory/import/page.tsx:132-170`). There is also a second CSV import surface on the main inventory page that still uses `csvService.processCSVFile(file)` (`app/dashboard/inventory/page.tsx:134-135`, `app/dashboard/_components/csv-upload.tsx:42-65`).
- Task 4: the current tax behavior is not just `tax_rates + suppliers`. `calculatePurchaseOrderTax()` also uses `get_tax_rate_details`, `upsert_cached_tax_rate`, supplier override/exempt flags, and the `/api/tax-rates` ZIP lookup (`src/infrastructure/services/taxService.ts:26-145`, `src/infrastructure/services/taxService.ts:249-317`, `app/api/tax-rates/route.ts:22-98`). Do not ship a simplified Rust-only DB lookup as “parity”.
- Out-of-scope section: fix the supplier-rating note. Supplier rating on receive is already a Postgres trigger, not a TS-only hook (`src/infrastructure/supabase/migrations/20240219000011_create_functions_triggers_phase2.sql:3-53`, `src/infrastructure/supabase/migrations/20240219000011_create_functions_triggers_phase2.sql:324-340`).
- Out-of-scope section: if notifications are truly deferred, say so as a known regression, not as “Postgres fires”. Manual PO approve/receive and manual reorder-trigger notifications are app-side today (`src/application/use-cases/purchase-orders/approve-purchase-order.use-case.ts:24-43`, `src/application/use-cases/purchase-orders/receive-purchase-order.use-case.ts:29-55`, `src/application/use-cases/reorder/create-reorder-purchase-order.use-case.ts:118-129`).

## Nice-to-haves
- Keep the new Postgres RPCs for `receive_purchase_order` and reorder-created POs. Under the current PostgREST adapter, that is the clean fix for the partial-commit behavior already present in `receivePurchaseOrder()` and `CreateReorderPurchaseOrderUseCase` (`src/infrastructure/services/purchaseOrderService.ts:434-512`, `src/application/use-cases/reorder/create-reorder-purchase-order.use-case.ts:86-116`).
- Keep DB triggers as the source of truth for `line_total`, `subtotal`, and `total_amount`; do not duplicate that math in Rust just to “defend” against trigger bugs. One live-Supabase integration test around item insert/update is higher value than dual logic (`src/infrastructure/supabase/migrations/20240219000006_create_purchase_order_items_table.sql:57-113`).
- Analytics deferral is low risk. The actual purchase-orders page computes stats from direct `purchase_orders` reads and does not use `IPurchaseOrderAnalyticsService`; that service only feeds the unused Zustand store (`app/dashboard/inventory/purchase-orders/_components/use-purchase-orders.ts:45-161`, `src/infrastructure/services/purchaseOrderAnalytics.ts:68-142`, `app/stores/purchaseOrderStore.ts:418-447`).
- If you keep a DB function for reorder-created POs, either reuse or clearly differentiate the existing `auto_create_purchase_order()` helper so S3c does not leave two overlapping database implementations (`src/infrastructure/supabase/migrations/20240219000011_create_functions_triggers_phase2.sql:111-214`).

## Questions I want answered before we start
- For tax: do you want S3c to proxy the existing TS tax calculation for parity, or to port the full current behavior including ZIPTAX/cache logic? I would not ship the simplified DB-only version in the draft.
- For notifications: are PO approve/receive and manual reorder-trigger notifications acceptable regressions for one release cycle, or do they stay in scope?
- For reorder cutover: are “Create Individual POs” and “Create Bulk PO” in-scope for S3c, or should the plan explicitly leave those buttons on legacy during the flag window?
- For PO status: are you comfortable making `received` terminal and reachable only via the dedicated receive flow, instead of preserving a generic status-edit path for it?
