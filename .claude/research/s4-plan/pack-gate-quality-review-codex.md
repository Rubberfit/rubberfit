# Pack-gate quality review — Codex

## Verdict: block

## Does the quality premise hold?
- No. The only checked-in benchmark sweep covers 9 parity fixtures x 3 modes x 2 seeds, and it shows identical placed/overflow/density across `fast`, `balanced`, and `thorough` for every fixture. Elapsed time still stays only 4-34 ms across the whole table. (`docs/superpowers/benchmarks/2026-04-18-s2.5-results.md:5-9,11-80`; `engine/crates/rf-layout/tests/bench_summary.rs:24-59,83-101`)
- The loop code matches the flat data. Single-bin search spends 100% of budget in exploration, then runs identity compression; `exploration_phase` returns immediately on the first feasible layout because density is fixed by the item set; multi-bin operators document zero density lift on the RF parity fixtures. (`engine/crates/rf-layout/src/infrastructure/search/mod.rs:12-23,98-145`; `engine/crates/rf-layout/src/infrastructure/search/gls/explore.rs:110-115,146-153`; `engine/crates/rf-layout/src/infrastructure/search/gls/compress.rs:23-32,47-71`; `engine/crates/rf-layout/src/infrastructure/search/multi.rs:50-66`)

## Recommended time budget
- Stay on `fast` / 2,000 ms. That already matches the live cut-planner request, and the checked-in benchmarks show no quality gain from 10,000 ms or 30,000 ms on the only measured fixture set. Actual observed runtimes are 4-34 ms, so the bigger budgets are theoretical wait, not demonstrated quality. Evidence is absent for real production cut-planner workloads beyond the nine parity fixtures. (`app/dashboard/cut-planner/_components/use-nfp-optimizer.ts:111-125,134-140,177-186`; `src/application/packing/types.ts:118-122`; `docs/superpowers/benchmarks/2026-04-18-s2.5-results.md:11-80`; `engine/crates/rf-layout/tests/bench_summary.rs:24-59`)

## Gate design review
- **450ms minimum loader: theater.** The hook always waits 450 ms before `done`, regardless of solver state, while the benchmark report's runs finish in 4-34 ms. That makes the loader 13x-112x longer than the measured pack time. (`app/dashboard/cut-planner/_hooks/use-pack-gate.ts:37-45,71-78`; `docs/superpowers/benchmarks/2026-04-18-s2.5-results.md:11-66`)
- **Invalidate-on-input-change: directionally correct, but incomplete.** The hook resets to `idle` on change and the design intends to hide stale layouts. But it is incomplete unless the UI also aborts in-flight packs. `usePackGate` explicitly does not reach into the packer, `useNfpOptimizer` cleanup only flips `mounted=false`, and the live pack call passes no `signal`, even though the service interface supports `AbortSignal`. (`app/dashboard/cut-planner/_hooks/use-pack-gate.ts:24-30,51-52,80-83`; `app/dashboard/cut-planner/_components/use-nfp-optimizer.ts:138-140,172-176`; `src/application/services/packing.service.interface.ts:14-23`)
- **Fake progress timer vs wiring `PackOptions.onProgress`: real progress is plumbed through the engine, but not to this UI today.** `PackOptions.onProgress` exists, `rustPackingService` switches to `--stream` and invokes callbacks, and the Rust integration test asserts a baseline progress frame. The cut-planner still calls `svc.pack(request)` with no options, the page still renders `NestingVisualizer` directly, and `pack-progress.tsx` is presentational-only. (`src/application/services/packing.service.interface.ts:14-23`; `src/infrastructure/services/rustPackingService.ts:52-60,87-90,183-193`; `engine/crates/rf-layout/tests/cancel_progress_integration.rs:127-144`; `app/dashboard/cut-planner/_components/use-nfp-optimizer.ts:138-140`; `app/dashboard/cut-planner/page.tsx:11-12,89,583-594`; `app/dashboard/cut-planner/_components/pack-progress.tsx:15-17,22-32`)
- **No cancel UI: not acceptable for any future 30s thorough path.** The engine already has cooperative cancel, and its integration test expects mid-search cancel within a 500 ms CI cap with a ~100 ms product SLA. The proposed progress component has no cancel affordance, and the live cut-planner path passes no `signal`. (`engine/crates/rf-layout/tests/cancel_progress_integration.rs:3-8,95-124`; `src/infrastructure/services/rustPackingService.ts:155-169,220-225`; `app/dashboard/cut-planner/_components/pack-progress.tsx:32-53`; `app/dashboard/cut-planner/_components/use-nfp-optimizer.ts:138-140`)

## Ship list
Ship only a trimmed version: keep `fast` / 2,000 ms, drop the fixed 450 ms minimum loader, keep invalidate-on-change but pair it with `AbortSignal` cancellation, wire `PackOptions.onProgress` into a real progress model instead of a timer, and add a visible Cancel action before exposing any mode that can run into multi-second territory. Otherwise this change trades a current auto-preview that debounces at 220 ms and repacks on every tracked input change for a manual Pack gate with no proven quality gain and a guaranteed first-render regression. (`app/dashboard/cut-planner/_components/use-nfp-optimizer.ts:134-140,177-186`; `app/dashboard/cut-planner/_hooks/use-pack-gate.ts:15-25,37-45`; `docs/superpowers/benchmarks/2026-04-18-s2.5-results.md:11-80`)

## What Gemini might miss
- The regression is not just one more click. Today the Graph card mounts `NestingVisualizer` as soon as there is a selected template, and that component immediately calls `useNfpOptimizer(...)`; the proposed gate explicitly starts page load and every input change in `idle` until the operator presses Pack. That means loss of live responsiveness, Pack as the only path to first render, and background stale-work risk unless invalidation is wired everywhere and in-flight work is aborted. (`app/dashboard/cut-planner/page.tsx:549-595`; `app/dashboard/cut-planner/_components/NestingVisualizer.tsx:394-403`; `app/dashboard/cut-planner/_hooks/use-pack-gate.ts:15-25,27-30`)
