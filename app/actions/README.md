# Server Actions

Server-only entrypoints that the client `await`s. Each action is a hard physical line between the browser and the orchestration layer — action IDs ship in the client bundle and are RPC-callable by hash, so the auth + RBAC + Zod-parse checks here **are the security boundary**. `proxy.ts` does not see action invocations.

## Mandatory shape

Every action file starts with `"use server"`. Every exported action follows this order (the security boundary depends on the order):

```ts
export async function actionName(input: ActionInput): Promise<ActionResult> {
  ensureDatabaseFactoryRegistered() // ← always first; idempotent
  const actor = await requireAuthenticatedUser() // throws UnauthorizedError
  requirePermission(actor, "manageRolls") // throws ForbiddenError
  const parsed = schema.parse(input) // strips extra keys; throws on bad input

  // Either:
  const useCase = resolveUseCase<IFoo>(TOKENS.IFoo)
  const result = await useCase.execute({ ...parsed, actor })
  // Or (simple ops with no use-case):
  const result = await someService.doIt({ ...parsed, actorId: actor.id })

  revalidatePath(RELEVANT_PATH) // server-side cache bust
  return result
}
```

**Exceptions to the `requirePermission` step:** `active-tenant.ts::selectTenant` (the action that establishes which tenant the actor is operating in — must run before any permission check is meaningful), `profile.ts::requestSelfDelete` (actor is always the target — no privilege-escalation surface), and `invitations.ts::acceptInvitation` (the token IS the auth — the use-case validates the invited org's subscription internally). All still run `ensureDatabaseFactoryRegistered()`, `requireAuthenticatedUser()`, and Zod-parse their input.

**Subscription gate (post-DDD merge, 2026-05-18):** `await requireActiveSubscription(actor)` runs as the immediately-next statement after `requireAuthenticatedUser` on every action **except** the recovery-allowlist (so a user with a lapsed/expired sub can still recover billing). The architectural test `tests/architecture/billing-actions-require-active-subscription.test.ts` enforces ordering + allowlist membership. Current allowlist: `selectTenant`, `requestSelfDelete`, all of `billing.ts` (modulo `updateSubscriptionSeatCount`), `getUserPreferences`/`updateUserPreferences`, `getOrganizationPreferences` (read), and both `acceptInvitation` variants (team.ts + invitations.ts).

Three error classes propagate across the RPC boundary: `UnauthorizedError` (401-class), `ForbiddenError` (403-class), `AuthConfigError` (5xx-class). Catch wrappers in client callers should discriminate on `error.code`, **not** `instanceof` — error prototype chains don't survive serialisation. The subscription gate throws `SubscriptionRequiredError` (`code: "NO_ACTIVE_SUBSCRIPTION"`) with a `recovery` discriminator (`complete_checkout` / `update_billing` / `restart_subscription` / `needs_workspace`).

Public input is `z.input<typeof schema>` (derived from the Zod schema) — not `Omit<UseCaseInput, "actor">`. The Zod schema is the source of truth for the runtime parse contract; using `z.input` keeps types and runtime in lockstep.

### `team.ts` ↔ `invitations.ts` duality

Both files independently expose `acceptInvitation` / `resendInvitation` / `revokeInvitation`, the merge artifact of two parallel sprints landing the same flow:

- `invitations.ts` (DDD branch, Phase 5/8) is the **canonical** surface — admin-members UI imports from here, return shapes use the DDD `AcceptInvitationResult` discriminator, accept writes the `rema_active_tenant` cookie.
- `team.ts` (dev branch, Stripe sprint) is still imported by `app/dashboard/settings/team/_components/*.tsx`. Its `acceptInvitation` wraps in try/catch and returns the legacy `{ organizationId, membershipId } | { error }` shape; `team.ts::deactivateMember` is unique to this file.

Both call into the same `IAcceptInvitationUseCase`. Consolidation is tracked separately — neither file is a no-op rename target without a full call-site audit. For now: prefer `invitations.ts` for new admin-side UI; touch `team.ts` only when changing the settings/team surface.

## When to wrap with a use-case vs. call services directly

Follow the same rule as the use-cases [README](../../src/application/use-cases/README.md): wrap in a use-case if the action fires a side effect (notification, audit log), touches >1 service, or enforces a business rule (status transition, EOQ, threshold). Otherwise call the infrastructure service directly from the action body — `materials.ts`, `inventory.ts`, `users.ts`, `profile.ts` are the live examples.

The action layer **always** stays. Even when there's no use-case, the action carries the auth + RBAC + Zod surface. Hooks must never call infrastructure services that mutate — those must go through an action.

## Patterns to copy

- **Use-case-wrapped + cache bust** → `purchase-orders.ts::createPurchaseOrder`
- **Direct-service + narrow field surface (security)** → `users.ts::updateUser`
- **Server-fetched authoritative state (no client-supplied payload)** → `reorder.ts::createReorderPurchaseOrder` (the file header explains why the previous payload-passing shape was a security gap)
- **Typed return for UX discrimination** → `profile.ts` self-delete `{ ok, error }`
- **No-revalidate (user redirects out)** → `profile.ts`

## Client-side responsibilities

Actions handle server cache invalidation with `revalidatePath`. The client must **also** call `queryClient.invalidateQueries({ queryKey: [...] })` after the action returns when the relevant data is read through React Query. Forgetting either side creates stale UI.
