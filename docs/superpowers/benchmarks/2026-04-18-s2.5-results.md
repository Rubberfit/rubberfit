## Task 18 tuning findings (2026-04-18)

Ran the full sweep twice: once with the Task 12 defaults
(`MAX_ROUNDS = 20`, `MAX_OPERATOR_GAP = 8`, `TERMINATION_NOOP_TICKS = 3`)
and once with triple-loosened constants (60 / 16 / 8). **Density,
placed count, and overflow were bit-identical across every fixture ×
mode × seed combination.** Elapsed time also converged within noise.

Root cause: the operator ladder (`unload_lightest_bin` → `migrate` →
`swap_two`) returns `Ok(None)` on the very first tick for every
fixture in the parity set. FFD's initial assignment is already at the
ceiling of the lex score `(closed_bins, concentration)` for this
fixture family — no swap, migration, or unload strictly improves the
metric. Extra rounds therefore never run, regardless of budget.

**Implication for Task 18:** the GLS + orchestrator are NOT the
density bottleneck on REMA's current fixture distribution. Real
density lifts will require one of:

1. A richer acceptance metric that lets `swap_two` commit on sub-metric
   improvements (e.g. adding a third component to the lex score).
2. Enabling item rotation (`allow_rotation: true`) on fixtures —
   currently all parity fixtures are `allow_rotation: false`, so
   no-rotation Pareto ceilings dominate.
3. Larger fixtures where FFD's greedy ordering genuinely traps
   improvable configurations (the parity set caps at ~20 items per
   fixture).

These are product / data decisions, not parameter-tuning decisions.
Keeping the conservative defaults (`20 / 8 / 3`) to minimize
worst-case wall-clock on future fixtures where operators *do*
iterate. Task 18 ships as calibration + this documented finding,
NOT as a density-lift change.

The Tasks 5-13 GLS + cross-bin swap infrastructure remains correct
and production-ready; it's just gated behind acceptance criteria
that the current REMA parity set does not exercise.
