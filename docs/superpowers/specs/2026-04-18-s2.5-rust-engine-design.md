# S2.5 Rust Engine — Industry-Competitive Nesting

**Status:** Design locked after parallel Gemini + Codex + academic literature review on 2026-04-18.
**Author:** Claude synthesis of three independent research reports (see §9).
**Predecessor:** `2026-04-17-s2-rust-engine-design.md` (S2 MVP shipped with warm-start greedy only).

## 1. Goal

Lift the Rust nesting engine from S2's warm-start-greedy MVP to an **industry-competitive 2D irregular bin-packer** that decisively beats the legacy TypeScript GA engine on quality, speed, and robustness — and holds its own against commercial nesting software (Deepnest, SigmaNEST, Nesting Analyst) on real cut-planner workloads.

Success = all of:
- **Quality:** ≥ +5% density on the parity fixtures over both (a) the TS GA engine and (b) S2 warm-start-only, averaged across the 9 fixtures.
- **Speed:** user-perceived responsiveness — Fast mode (~2s) is always interactive, Balanced (~10s) for typical jobs, Thorough (~30s) as a "optimize overnight" option.
- **Progress streaming:** per-iteration `bestLayoutSoFar` emitted so the UI can show improving layouts live, and the user can accept best-so-far early.
- **Cancellation:** a running pack can be cancelled cleanly (Tauri `AbortController` wiring from S4 uses the same mechanism).
- **Determinism:** seed-reproducible runs when `seed` is set.

## 2. Algorithmic recipe (locked)

The three independent research passes converged on the same recipe. The academic literature, the sparrow paper (Gardeyn et al., arXiv 2509.13329), and the practical bin-packing literature (Cai et al. 2023, Martinez-Sykora 2017) all endorse:

```
┌─────────────────────────────────────────────────────────────┐
│ OUTER: First-Fit-Decreasing bin assignment + cross-bin swap │
│                                                             │
│   for each bin (largest-area-first items):                  │
│     ┌─────────────────────────────────────────┐             │
│     │ INNER: sparrow-style per-bin optimizer  │             │
│     │   Phase 1 (80%): exploration via GLS    │             │
│     │                  with penalty weights   │             │
│     │   Phase 2 (20%): compression (polish)   │             │
│     └─────────────────────────────────────────┘             │
│                                                             │
│   final: cross-bin swap operators on top-k heaviest bins    │
└─────────────────────────────────────────────────────────────┘
```

This is exactly what Cai et al. (2023), the best published 2D-irregular-BPP paper, prescribes. It's also what Deepnest and SigmaNEST do in production. Sparrow's contribution (the GLS inner optimizer) is empirically +0.2–4% density over prior published best on ESICUP, and we inherit that.

## 3. Key decisions

### 3.1 Sparrow: vendored-reference, not linked-crate

Sparrow's `optimize(SPInstance, …) -> SPSolution` is SPP-coupled and cannot be used as a crate dependency for our BPP workload. We **vendor its GLS core** (license: MIT, `ejor-snapshot` tag, commit `c95454e3`) into a private `engine/crates/rema-layout/src/infrastructure/search/` module and rewrite it against jagua-rs BPP primitives (`BPProblem::{place_item, remove_item, save, restore, density}` — §4 of Gemini's report confirmed these are complete).

Port minimally: preserve sparrow's `Separator`, `CollisionTracker` (which is already BPP-compatible — `Layout`-generic), penalty-weight loop, and parallel sampling workers. Replace sparrow's `change_strip_width` objective with a BPP objective: **maximize placed-item area subject to fixed (bin.width, bin.height)**.

### 3.2 Bin-assignment layer written fresh

Sparrow has no bin-assignment logic (it's strip-packing). We write our own small FFD + cross-bin-swap layer. ~300–500 LOC of Rust, well-understood from published heuristics (Martinez-Sykora 2017 "jostle," Cai 2023 "block-building").

### 3.3 Progress + cancellation are first-class

The current `OptimizerConfig` grows:
```rust
pub struct OptimizerConfig {
    pub time_budget_ms: u64,
    pub improvement_budget_ms: Option<u64>,
    pub seed: Option<u64>,
    pub progress_callback: Option<ProgressCallback>,  // NEW
    pub cancel_token: Option<Arc<AtomicBool>>,        // NEW
}
pub type ProgressCallback = Arc<dyn Fn(PackProgress) + Send + Sync>;
```

`PackProgress` carries `{ iteration, elapsed_ms, best_layout_so_far, phase }`. Over the CLI boundary it becomes newline-delimited JSON on stdout — one JSON object per `bestLayoutSoFar` improvement, with the final result last. TS reads via `child.stdout.on("data")` line-buffered.

### 3.4 Phased delivery

| Phase | Scope | Duration | Quality lift |
|---|---|---|---|
| **S2.5a** | Port sparrow GLS into `search/` (single-bin optimizer), replace `sparrow_driver::optimize` | 1-2 weeks | +3–5% density single-bin |
| **S2.5b** | FFD bin assignment + cross-bin swap operators + multi-bin coordination | 1-2 weeks | +2–5% density multi-bin |
| **S2.5c** | Progress streaming, cancellation, benchmark harness, REMA-specific tuning pass | 1 week | polish |

Total: **3-5 weeks**. Tag `s2.5-industry-competitive` on completion.

### 3.5 Rejected alternatives (and why)

- **Pure sparrow-per-bin SPP-decomposition (Gemini path b):** Fastest to ship (1 week), but SPP/BPP coordinate translation is brittle and we'd need to re-fork once we add cross-bin moves anyway. Rejected — does the work twice.
- **packingsolver (C++ via FFI):** Codex surveyed; C++ leaks into build, license is fine but we lose Rust-native testability and clean-architecture story. Kept as offline benchmark oracle only.
- **Deepnest / SVGnest (JS-via-worker):** Slower, GPL-3.0, not competitive with sparrow quality. Dismissed.
- **OR-Tools CP-SAT:** Irregular polygon support requires rasterization; doesn't hit 2s budget. Useful only for small-instance validation.
- **RL/GFPack++:** Academic consensus says ML is 2–3 years from ESICUP-quality production; ruled out for v1.

## 4. Architecture

New layout under `engine/crates/rema-layout/src/infrastructure/`:

```
infrastructure/
├── jagua_adapter.rs              (existing)
├── warm_start.rs                 (existing — becomes the S2.5a seed feeder)
├── sparrow_driver.rs             (existing stub — removed, replaced by search/)
└── search/                       (NEW S2.5a + S2.5b)
    ├── mod.rs                    — pub fn optimize(seed, config) -> Result<SeedResult>
    ├── state.rs                  — multi-bin incumbent, unplaced queue, score cache
    ├── objective.rs              — lexicographic BPP objective (overflow → bins → waste)
    ├── gls/                      — vendored-and-adapted sparrow GLS
    │   ├── mod.rs
    │   ├── separator.rs
    │   ├── explore.rs
    │   ├── compress.rs
    │   ├── penalty.rs
    │   └── sampling.rs
    ├── assignment/               — BPP-native bin assignment (fresh code)
    │   ├── mod.rs
    │   ├── ffd.rs                — First-Fit-Decreasing with area-desc / longest-edge
    │   └── cross_bin_swap.rs     — swap-two / remove-insert move operators
    ├── progress.rs               — ProgressCallback plumbing
    └── cancel.rs                 — cooperative cancellation (AtomicBool polled in hot loops)
```

Domain + application layers unchanged. `pack.rs` orchestrator keeps its per-bin loop but now the inner call goes through `search::optimize(seed, config)` (same signature as today's `sparrow_driver::optimize`).

## 5. Data flow (full run, Balanced mode = 10s budget)

1. TS calls `RustPackingService.pack(req)`. pack-cli receives JSON on stdin.
2. pack-cli calls `rema_layout::application::pack(request)`.
3. `pack()` validates and sets up per-bin budget (`10_000 / bins.len()` ms).
4. For each bin:
   a. Build `BPInstance` via `jagua_adapter::to_jagua_instance`.
   b. Run `warm_start::greedy_bottom_left` → `SeedResult { placements, overflow }`.
   c. Call `search::optimize(seed, cfg)`:
      - **S2.5a only:** runs GLS against this single bin.
      - **S2.5b:** GLS per bin + cross-bin swap pass every K iterations.
      - Emits progress events on `cfg.progress_callback`.
      - Checks `cfg.cancel_token` every N iterations → returns best-so-far if triggered.
   d. Accumulate final placements, decrement remaining quantities.
5. Return `PackResult` + newline-delimited progress log on stdout.
6. TS reconstructs placements, calls `buildPlacementView` for rendering.

## 6. Benchmark harness (S2.5c deliverable)

Create `engine/crates/rema-layout/benches/` using `criterion`:
- All 9 parity fixtures × 3 modes (Fast / Balanced / Thorough) × 2 seeds.
- Metrics per run: density %, placed count, overflow count, wall-clock ms, memory high-water.
- Comparison rows: TS GA baseline (snapshot from parity tests) + S2 warm-start + S2.5 final.
- Output: Markdown table committed to `docs/superpowers/benchmarks/2026-04-18-s2.5-results.md`.
- CI guardrail: fail the build if S2.5 regresses > 1% on any fixture.

## 7. Public API changes

TypeScript side (additive, non-breaking):
- `PackRequest.cancelTokenId?: string` — opaque handle for cooperative cancellation; pack-cli reads from stdin after the initial JSON is drained.
- `PackProgress` interface already exists in `src/application/packing/types.ts` — unchanged on TS side; now actually emitted.
- `IPackingService.pack(request, onProgress?)` — second parameter already exists; `RustPackingService` now wires it through.

Rust side:
- `OptimizerConfig` gains `progress_callback` + `cancel_token` (§3.3).
- `PackResult` gains `iterations: u64` and `converged: bool` for telemetry.

## 8. Out of scope

- Rewriting jagua-rs (stays at 0.7.1).
- Continuous rotation optimization in the search loop (allowed, but neighborhood operators sample discrete angles — matches sparrow's actual behavior).
- Sheet defects / containers with holes (out for v1; jagua-rs supports it, so can land in S5/S6).
- Learned-policy warm starts (ML hybrid is 2–3 years from production-grade per academic consensus).
- Parallel multi-bin search (each bin remains sequential; parallelism is inside sparrow sampling).

## 10. Risks

Consolidated from the three reports:

1. **Sparrow porting risk:** reimplementing the GLS loop against BPP primitives risks introducing bugs that don't exist in the SPP upstream. Mitigation: property tests asserting "placed items never collide," snapshot tests against a reference run.
2. **f32 precision:** jagua-rs uses f32. Large stock dimensions (> 16384 inches) lose sub-millimeter precision. Add a pre-flight check in `jagua_adapter.rs` that warns when dimensions exceed a safe threshold.
3. **Convex-hull vs exact polygon behavior change:** the TS engine uses convex hulls for NFP; sparrow/jagua-rs use exact polygons. Cone/annular-sector parts will pack differently — in principle better, but visually different. Flag in rollout notes.
4. **Progress monotonicity:** GLS can temporarily worsen density during exploration. UI must show only best-so-far, never the live iterate (otherwise utilization appears to decrease). Enforced in `progress.rs`.
5. **Cancellation timing:** cooperative cancellation via `AtomicBool` is checked every N iterations. If N is too large, UI cancel feels sluggish. Target: ≤ 100ms worst-case response.
6. **Tuning time:** academic papers don't report the tuning burden. Realistic estimate from the reviews: 4–8 weeks of experimentation on REMA's shape distribution to close the last 2-3% density gap vs. academic best-on-ESICUP. Budget this into S2.5c.
7. **License:** sparrow is MIT (verified via GitHub API), not MPL-2.0. Ports are free-license; no copyleft surface.
